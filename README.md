# Offline Board Games

**圏外でも、みんなで遊ぼう。** フェリーや旅行先で、友人と遊ぶためのスマートフォン向けボードゲーム集です。日本語UI、アカウント不要、広告・解析・バックエンドDBなし。初回の保存後は外部インターネットなしで起動できます。

> 1台で2〜7人対戦はネットワーク不要です。複数端末での対戦は、端末同士の通信を許可した同じLANが必要です。テザリングの機種・OS・ネットワーク設定によっては接続できません。**乗船前に、実際に持っていく全端末で必ず試してください。**

## Features

- 既存の2人用5ゲーム＋追加24ゲーム＝全29ゲーム。1台を囲む／各自の端末で遊ぶモードに対応
- 2人用5ゲームに持ち時間・1手ごとの加算・秒読み。大富豪の7つの選択ルールなど、ゲーム前に設定
- 2〜7人の部屋、手札を持ち主だけへ配信、変更部分だけを同期、全員承認による再戦
- アプリ本体・全ゲームエンジン・QR生成/読取・アイコンの事前キャッシュ
- 実際のキャッシュ内容を検査する「オフライン準備」表示
- iPhone用インストール案内、Androidのインストールプロンプト
- QRの圧縮・分割・カメラ読み取り、テキスト表示/入力/コピー/貼り付け
- サーバーを介さないWebRTC DataChannel通信、切断時の再接続とホストからの盤面再同期
- 合法手の表示、昇格/成り選択、持ち駒、手番、投了、再戦、盤面反転
- 時計なしの2人用ローカル対局の再開、終了した対局の履歴（2人用・多人数それぞれ100件）、テーマ・サウンド・Debug設定
- 320px幅への対応、OSのダークモード、キーボード操作

チェスの3回同形・50手は申告操作を省き自動引き分けにしています。将棋の入玉宣言・持将棋の点数裁定・大会の500手規定は実装していません。時計は友人同士向けの独自設定です。千日手は引き分けを記録し、再戦できます。既存5ゲームは2000手、追加24ゲームは10,000操作を安全上の上限とし、到達時は引き分けです。詳しい設計判断は [ARCHITECTURE.md](ARCHITECTURE.md) を参照してください。

### 多人数ゲームと選択ルール

ホームでは名前と人数で全29ゲームを絞り込めます。選択した人数・名前・ルール・時計はゲーム別にこの端末へ保存します。

追加のマンカラ（カラハ）は2人、石取り（ニム）・ドミノ・ヨット・ダイスは2〜7人。石数や最後の石の勝敗、ドロー／ブロック式、ロール回数・ボーナスなども選べます。

大富豪、七並べ、ババ抜き、ジジ抜き、クレイジーエイト、ゴーフィッシュ、神経衰弱、ピッグ・ダイス、ドット＆ボックスは2〜7人。ダウトとハーツは3〜7人です。ゲームごとの人数・選択項目・地域ルールとの差・調査元を [docs/RULES.md](docs/RULES.md) にまとめています。

大富豪は革命・8切り・11バック（Jバック）・マーク縛り・スペ3返し・階段・禁止札上がりを選べます。再戦の階級や札交換は引き継がないハウスルールです。人数の拡張や、通信速度に左右されない順番制ダウトなども、アプリ内の説明に明記しています。

## Technology

### すぐ遊べるゲームも追加

かんたん麻雀、ヒット＆ブロー、ハイ＆ロー、数字の地雷、ひみつじゃんけん、ワードウルフ、ジェスチャー、21カウント、三目並べを追加しました。会話や動きで遊ぶゲームも1台共有・複数端末で利用できます。麻雀は役・符計算・鳴きなしの入門版です。詳しい採用ルール・調査元は [docs/CASUAL_GAMES.md](docs/CASUAL_GAMES.md) を参照してください。

### 実装技術

React / TypeScript strict / Vite / vite-plugin-pwa / Workbox / Service Worker / WebRTC RTCDataChannel / localStorage / Vitest / ESLint / Playwright。

チェスは `chess.js`、QR生成は `qrcode`、QR読取は `jsQR`、接続情報の圧縮は `fflate` を使用します。すべてビルドに含まれます。実行時CDN、Google Fonts、Analytics、広告、外部API、STUN/TURNサービスへの依存はありません。フォントと駒の文字は端末のシステムフォント、装飾はCSS、アイコンは同梱ファイルです。音は端末内のWeb Audioで生成します。

## Development

Node.js **22.12以上**（CIは24）、npmを用意します。

```bash
npm install
npm run dev
```

開発サーバーではService Workerを有効にしていません。PWAの検証には本番ビルドとプレビューを使います。カメラ・Service WorkerはHTTPSまたはlocalhostが必要です。別のスマートフォンから `http://PCのIP:5173` を開くだけでは、これらの機能を正しく検証できません。実機ではGitHub PagesのHTTPS URLを使用してください。

## Deployment — GitHub Pages

このプロジェクトの現在の保存先は個人アカウント `TOMO0904/offline-board-games`（非公開）です。GitHub Freeの非公開リポジトリではPagesを利用できないため、この構成ではVercelへインポートして配信します。VercelのFrameworkをVite、Build Commandを `npm run build`、Output Directoryを `dist` にします。`BASE_PATH` は未設定（`/`）で使用し、GitHubへのアクセス許可は対象リポジトリだけに限定できます。友人へ渡すのは本番の `*.vercel.app` URLです。リポジトリを非公開にしても配信アプリ自体は公開され、配信されたJavaScriptは閲覧可能です。

以下はGitHub Pagesを使う場合の手順です。workflowは非公開リポジトリではPagesデプロイをスキップします。有料プラン等でPagesを利用できる非公開リポジトリでは、Repository variable `ENABLE_GITHUB_PAGES` を `true` にした場合だけデプロイします。

無料運用にはGitHub Freeの**公開リポジトリ**を使用します。アプリのホスティング以外にサーバーは不要です。

1. GitHubに公開リポジトリを作成し、このプロジェクト一式を `main` ブランチへpushします。`package-lock.json` も含め、`node_modules` と `dist` は含めません。
2. リポジトリの **Settings → Pages → Build and deployment → Source → GitHub Actions** を選びます。
3. **Actions** で `Validate and deploy GitHub Pages` を確認します。必要なら **Run workflow** で再実行できます。
4. インストール、Lint、型チェック、Unit/E2Eテスト、本番ビルドの成功後に自動で公開します。
5. `https://USERNAME.github.io/REPOSITORY/` を両端末で開きます。

[.github/workflows/deploy.yml](.github/workflows/deploy.yml) がリポジトリ名から `BASE_PATH` を設定します。`main` へのpushでデプロイ、Pull Requestでは検証のみです。デプロイ用権限はdeployジョブの `pages: write` と `id-token: write` だけに分離しています。GitHubのEnvironmentに手動承認ルールを追加している場合はその承認が必要です。

`USERNAME.github.io` という名前のユーザーサイトや独自ドメインのルートに配置する場合は、workflowの `BASE_PATH` を `/` に変更してください。本プロジェクトに公開先リポジトリや認証情報は含めていません。ローカルフォルダーだけで作成した場合は、Gitリポジトリの作成とpushが必要です。

[GitHub公式: カスタムworkflowによるPages公開](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)

## Offline Preparation

Service WorkerはHTML/JS/CSS/manifest/アイコンと全ゲーム・QR処理を事前キャッシュします。遅延してネットから取得するゲーム素材はありません。ホームの準備表示はService Workerへ問い合わせ、**現在のprecache manifestに記載された全ファイルがCache Storageに存在すること**を検査します。単なる `navigator.onLine` やインストール済みフラグでは判定しません。

「準備未完了」の場合は通信できる場所で開いたまま待ち、「再確認」を押します。空き容量不足やキャッシュ欠損が続く場合は、ブラウザのサイトデータを削除してオンラインで再インストールしてください（履歴と保存対局も失われます）。「保存領域を保護」はStorage Persistence APIへ保存保護を要求します。許可の判断はブラウザが行い、保存の永続保証はありません。

新しいバージョンはホームに更新ボタンが表示されます。**対局中に自動再読み込みしません**。対局を終えてから更新してください。旅行前に機内モードで再起動するテストも行ってください。

## Local Multiplayer

### この端末で2人

ゲームを選択 → 持ち時間を選ぶ → **この端末で2人**。交互に操作します。時計なしならホームから盤面を再開できます。時計付きは「時計を開始して対局」を押して開始し、画面終了・再読み込みで途中対局は失われます。「リセット」で新しく開始します。チェス/将棋は「盤面を反転」、五目並べは「盤面を拡大」を利用できます。

### 近くの端末と対戦

1. 2台を同じWi-Fi、または片方のテザリングに接続する。
2. 両方で同じゲーム → **近くの端末と対戦**。
3. Aで **対戦を作成**。Aがホストで、黒/先手/チェスの白です。
4. Bで **対戦に参加 → QRを読み取る**。AのQRが複数なら矢印で切り替えてすべて読む。
5. Bの返信QRをAで読み取る。こちらも複数ならすべて読む。
6. 両方の **接続完了** を確認して対戦する。

カメラを使えない場合は **接続テキストを表示・コピー** と **テキストで接続する** を使います。コピー/貼り付け権限がない場合はテキスト欄の長押しメニューが使えます。別の端末へ文字列を移す手段は自分で用意する必要があります。アプリはインターネット経由で文字列を転送しません。

切断時は盤面の操作を止めます。**ホストは同じ対局画面のまま「接続情報を作り直す」** を押し、ゲストが「対戦に参加」してQRを交換し直します。ゲストがホストの盤面を検証して復元します。通信対局はページ再読み込みやホームへの移動をまたいで継続しません。ホストの画面を閉じると対局途中の通信状態は失われます。

### 3〜7人で各自のスマホを使う

1. 全員が同じWi-Fiに接続し、同じ追加ゲームを選択。
2. ホストが人数・名前・ルールを設定し、「近くの端末と対戦」→「対戦を作成」。参加者は自分の端末で「対戦に参加」。
3. ホストが「接続する相手の席」を選び、「この席の接続情報を作る」。その人とだけQRを往復交換。
4. 残りの参加者にも繰り返し、全員が接続済みになったら「全員でゲーム開始」。参加者の人数・ルールはホストから同期されます。
5. 手札は持ち主の画面だけに表示。1台モードでは次の人へ渡して「自分の手札を表示」を押します。
6. 切断した人がいれば全員の操作を停止。ホストがその席のQRを作り直すと同じ手札で復旧できます。他の席の接続は維持します。
7. 再戦は全員が「再戦・リセット」を承認すると開始。ホストが終了・再読み込みすると部屋は失われます。

ホストは山札・全手札を管理するため、開発者ツールを使えば内容を見られます。友人同士で信頼できる端末をホストにしてください。参加者へ配られる情報は自分の手札と公開情報だけです。隠された山札・他人の手札・乱数シードは送信しません。途中の追加ゲームは保存せず、結果だけを保存します。

## How P2P connection works

```
Host                                  Guest
create RTCPeerConnection               same Wi-Fi / hotspot
iceServers: []
create ordered RTCDataChannel
createOffer → setLocalDescription
wait for ICE gathering complete
SDP → deflate → base64url → QR   →      scan offer → setRemoteDescription
                                      createAnswer → wait for complete
setRemoteDescription(answer)   ←       compressed answer QR
            ←—— encrypted DTLS / SCTP DataChannel ——→
hello / ready / game_start
move + sequence + state digest ←→      validate turn / legal move / digest
state_request                  →      host sends state_sync when needed
```

`iceServers: []` でホスト候補のみ収集し、STUN/TURNサービスへ問い合わせません。ICE自体の疎通確認やmDNS名前解決はローカルネットワークで発生します。ゲーム中の通常メッセージは指し手・連番・小さな整合性ダイジェストです。画像・音声・毎手の完全盤面は送りません。2人用は画面表示中30秒に1回、追加ゲームは接続ごとに60秒に1回ping/pongを送ります。対局時計はローカル描画し、毎秒の通信はありません。

順序飛び、盤面ダイジェスト不一致、再接続時にホストを正として `state_sync` します。復元時は開始局面からすべての手を再検証します。これはローカルの友人同士の対戦向けであり、不正なホストに対する競技用の公正性保証ではありません。

シグナリングは最大48,000文字、展開後SDPは最大32,000文字。QR1枚は接続文字列550文字までとし、複数枚を順不同で読めます。ゲームメッセージは最大200,000文字。長い盤面同期は16KiB未満のフレームに分割し、受信側で上限・期限・整合性を検査して復元します。受信データをHTMLとして実行しません。カメラは読み取り画面でのみ動き、終了時に停止し、撮影画像は送信・保存しません。

### 多人数の通信量

ホストを中心にしたスター構成で、7人でも接続は6本。通常は操作と、プレイヤーごとの公開情報・自分の手札の**差分**を送ります。完全な個別ビューは初回と再同期でのみ使用し、全員の隠し状態は送りません。ラウンド開始や再戦では新しい手札に必要な更新が発生します。

7人の七並べの通常パス操作について、6人への差分メッセージの合計が**4KiB未満**であることを自動テストしています。これはUTF-8のアプリペイロードで、IP/UDP/DTLS/SCTPやICEのオーバーヘッドを含みません。全てのゲーム・全操作の上限保証ではありません。設定のDebug画面では接続ごとの送受信ペイロードbytesと件数を確認できます。追加ゲームのパケット上限は32,000文字です。

## Ferry usage

**乗船前（インターネットあり）**

1. A/BともSafari/Chromeからインストールする。
2. ホーム画面のアプリを一度起動する。
3. 「オフライン利用可能」を確認する。
4. 遊びたいゲームを開き、機内モードでも再起動できることを確認する。
5. 実際に持っていく全端末・予定のテザリングでP2P接続テストを行う。

**フェリー上（外部インターネットなし）**

1. 片方がテザリング / Personal Hotspotを開始する。
2. 相手がそのWi-Fiへ接続する。インターネットに出られなくても、Wi-Fi接続を維持する。
3. 両方でOffline Gamesを起動する。
4. 同じゲームを選ぶ。
5. 「近くの端末と対戦」を選ぶ。
6. ホストが「対戦を作成」でQRを生成する。
7. ゲストがホストのQRを読む。
8. ホストがゲストの返信QRを読む。
9. 「接続完了」を確認する。
10. 対戦する。画面をロックせずアプリを前面に置く。

対局は外部インターネットを必要としません。ただし回線が圏外の状態でテザリングそのものを開始/維持できるかはOS・機種・契約によります。うまくいかなければ通常のWi-Fiや別端末のテザリングを試し、難しい場合は「この端末で遊ぶ」モードで遊んでください。

| コピー/貼り付けが拒否される | テキスト欄を長押ししてOSメニューから操作                                                                             |
| QRが読めない                | 相手の画面の明るさを上げる、映り込みを避ける、距離を調整。全分割QRを読む。別セッションが混ざったら読み取りをリセット |
| 接続候補がない              | Wi-Fiとローカルネットワーク権限を確認。OSのプライバシー制限の可能性。別ブラウザ/ネットワークを試す                   |
| 接続候補はあるが失敗        | 同じLANか、ゲストWi-FiやAP isolationで端末間通信が禁止されていないか、mDNS/UDPが遮断されていないか確認               |
| 画面ロック後に切れた        | 両画面を前面に戻す。ホストが同じ画面から接続情報を作り直し、双方のQRを交換                                           |
| 盤面が違う                  | 「盤面を再同期」。ホストの正しい盤面へ戻る。未到達だったゲストの最後の一手は取り消される場合がある                   |
| 新旧アプリでつながらない    | 乗船前に両端末を同じバージョンへ更新し、接続情報を新しく作る                                                         |
| 履歴が保存されない          | ブラウザのストレージ設定、空き容量、プライベートモードを確認                                                         |

**設定 → 接続Debugを表示** をONにすると、通信画面で `connectionState`、`iceConnectionState`、`iceGatheringState`、`signalingState`、DataChannel状態、双方の候補、送受信数/バイト数、最終sequence、matchId、stateHashを確認できます。IPや接続情報を含むため、Debug画面やQRを公開しないでください。

## Limitations

- iPhone Personal Hotspot、Android hotspot、通常Wi-Fi、端末の組合せは別々の条件です。iPhone同士・iPhone↔Android・Android同士で実機検証が必要です。
- クライアント隔離、mDNS不通、UDP遮断、WebRTCのホスト候補制限、ローカルネットワーク権限、テザリングのホスト/参加端末間通信制限により、同じSSIDでも接続できない場合があります。STUN/TURNを追加して誤魔化す実装はありません。
- カメラやBluetoothは接続情報の交換/補助であり、ネットワークの端末間通信制限を解除できません。カメラの許可を通信成立の必須条件にしていません。
- 電波圏外のテザリング、iOS/Androidのインストール、カメラの実機認識はデスクトップ自動テストだけでは保証できません。
- OSによるキャッシュ削除・省電力・バックグラウンド停止・ブラウザの保存容量制限には従います。
- 状態ダイジェストは同期不一致検出用で、署名や本人確認ではありません。近くにいる信頼できる相手とQRを交換してください。
- 15×15の全体盤面を320pxに収めながら全マス44pxを確保することはできません。五目並べは確定ボタン、横スクロール可能な拡大盤、キーボードを提供します。その他の盤面もマス以外の主要操作は44px以上です。
- コンピューター対戦、遠隔インターネット対戦、自動相手発見、観戦、サーバーへの履歴同期はありません。
